Webex Focus

Mute Webex. Get pinged only for the messages that matter to you. Catch up on everything else when you're ready, by asking your AI assistant.

Webex can't filter its own notifications. Webex Focus does the filtering for you: a small service reads every new message, checks it against your rules, and a bot re-sends only the important ones into the one chat you keep unmuted.

How it works

Two small programs and one database

The listener runs all the time and decides what happens to each message. The MCP server lets you manage rules and read summaries from Claude Code or VS Code Copilot. They never talk to each other directly; they share one SQLite file.

What happens to a message

Every message gets one of four statuses

notify

Important. The bot pings you right away.

digest

Not urgent. Held silently and included in your summary.

ignore

Noise. Held silently, left out of summaries, still searchable.

self

Your own replies. Kept so summaries show both sides.

Rules match on sender, space, keyword, or @mention. When several match, the strongest wins: ignore, then notify, then digest. If nothing matches, an @mention notifies and everything else goes to the digest.

[notify] manager@…  in a direct message: 'can you review this?'   (rule#3 sender=manager@…)
[digest] colleague@… in Team Chat: 'lunch anyone?'                 (default)
[notify] colleague@… in Team Chat: '@you quick question'           (rule#1 mention)
[self]   you@…       in Team Chat: 'on it'                         (self)

Design choices

Why it's built this way

Two ways to receive messages

Webhook: Webex calls us the instant a message arrives. Needs a public URL, which ngrok provides from a laptop.

Polling: we ask Webex every 10 seconds. Slightly slower, but it only makes outgoing requests, so it works on a company network where tunnels are blocked. It also catches up after downtime.

Rules, the bot, and summaries behave the same in both modes.

Our own MCP server, not Webex's

Webex now hosts MCP servers, but they only wrap the Webex API. They can't filter in real time, don't know our rules or why a message was held, and need an org admin to enable them.

Our server exposes our own data: rules, statuses and reasons, and saved summaries. It's one small Python file that runs locally.

Limits

What it doesn't do

  • It can't stop Webex's own notifications. You mute your noisy spaces once in the Webex app; the bot's chat stays unmuted.
  • It only knows messages from after the listener first started. There's no history import.
  • In webhook mode, messages sent while the listener is off are missed. Polling mode catches up.
  • It's a POC on personal free Webex accounts, running on a laptop. Nothing here is production-hardened.
Built with Python, FastAPI, SQLite, the official MCP SDK, and the Webex REST API. Plan and details live in the repo under docs/.
